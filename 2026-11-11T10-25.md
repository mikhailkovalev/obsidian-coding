## ChatGPT 5.4
Да. Чаще всего это называется **Event Sourcing**.  
  
Идея в том, что в БД хранят не “текущее состояние” сущности как одну запись, а **последовательность событий/операций**, которые это состояние меняли:  
  
- создано  
- изменено  
- удалено  
- восстановлено  
- сменился статус  
- изменился адрес  
- и т.д.  
  
Обычно каждое событие содержит:  
  
- тип события  
- время  
- кто выполнил  
- идентификатор сущности  
- данные изменения  
- иногда версию, correlation id, causation id  
  
### Как это выглядит  
  
Вместо таблицы вида:  
  
```sql  
users(id, name, status, updated_at)  
```  
  
может быть таблица событий:  
  
```sql  
events(  
  event_id,  aggregate_id,  aggregate_type,  event_type,  event_time,  actor_id,  payload,  version)  
```  
  
Примеры событий:  
  
- `UserCreated`  
- `UserNameChanged`  
- `UserBlocked`  
- `UserDeleted`  
  
Текущее состояние пользователя получается применением всех событий по порядку.  
  
---  
  
### Смежные термины  
  
Важно не путать с близкими подходами:  
  
#### 1. Audit Log / Журнал аудита  
Если вы храните обычные таблицы состояния, а рядом логируете “кто и что поменял” — это **аудит**, а не обязательно Event Sourcing.  
  
#### 2. Temporal tables / System-versioned tables  
БД сама хранит историю версий строк. Это история состояния по времени, но не всегда история именно бизнес-событий.  
  
#### 3. CDC (Change Data Capture)  
Это снятие изменений из БД, например из WAL/binlog. Полезно для интеграций, но это не то же самое, что проектировать систему вокруг событий.  
  
#### 4. CQRS  
Часто идет вместе с Event Sourcing, но это отдельная идея:  
- командами изменяем состояние  
- запросами читаем из отдельной модели чтения  
  
Event Sourcing **может** использоваться без CQRS, и наоборот.  
  
---  
  
### Когда этот подход полезен  
  
Он особенно хорош, если вам нужно:  
  
- полная история изменений  
- воспроизводимость состояния на любой момент  
- трассируемость “кто, что, когда сделал”  
- бизнес-доменные события как первичный источник истины  
- интеграции через публикацию событий  
- возможность “переиграть” состояние заново  
- сложная предметная область с важной историей изменений  
  
Типичные области:  
  
- финтех  
- бухгалтерия  
- документооборот  
- workflow-системы  
- склад/заказы  
- системы с сильными audit/compliance требованиями  
  
---  
  
### Плюсы  
  
#### 1. Полная история  
История изменений встроена в саму модель данных.  
  
#### 2. Отличный аудит  
Легко ответить:  
- кто изменил  
- когда изменил  
- что именно произошло  
  
#### 3. Восстановление состояния  
Можно восстановить состояние на любой момент времени, если события полные и упорядоченные.  
  
#### 4. Гибкость интеграции  
События удобно публиковать во внешние системы.  
  
#### 5. Отладка и анализ  
Можно понять, как система пришла к текущему состоянию.  
  
#### 6. Возможность строить разные представления  
Из одного потока событий можно строить разные read-модели:  
- для API  
- для отчетов  
- для поиска  
- для аналитики  
  
---  
  
### Минусы и проблемы  
  
#### 1. Сложнее читать текущее состояние  
Нельзя просто сделать `SELECT * FROM users WHERE id = ...`, если состояние вычисляется из длинной истории событий.  
  
**Решения:**  
- снапшоты  
- materialized views / read models  
- CQRS  
- кэширование  
  
---  
  
#### 2. Сложнее проектирование  
Нужно моделировать не таблицы, а **события домена**.  
  
Плохое событие:  
- `UserUpdated`  
  
Лучше:  
- `UserEmailChanged`  
- `UserActivated`  
- `UserAddressChanged`  
  
**Решения:**  
- event storming  
- DDD-подход  
- четкая схема именования событий  
  
---  
  
#### 3. Эволюция схемы событий  
Формат событий со временем меняется, а старые события уже записаны и должны остаться читаемыми.  
  
**Решения:**  
- versioning событий  
- upcasters / transformers старых событий в новый вид  
- backward compatibility payload-ов  
- schema registry  
  
---  
  
#### 4. Производительность при длинной истории  
Если у сущности тысячи событий, пересобирать состояние дорого.  
  
**Решения:**  
- snapshots каждые N событий  
- хранение готовых read-моделей  
- разбиение aggregate-ов  
- ограничение размера потоков событий  
  
---  
  
#### 5. Сложность удаления данных  
В event sourcing события часто считаются **immutable**. Но есть GDPR/152-ФЗ/политики удаления.  
  
**Решения:**  
- не хранить лишние персональные данные в payload  
- шифрование чувствительных данных и удаление ключей  
- псевдонимизация  
- event redaction  
- вынос PII в отдельное хранилище  
  
---  
  
#### 6. Трудно исправлять ошибки  
Если записали неверное событие, его обычно не “правят”, а добавляют компенсирующее событие.  
  
**Решения:**  
- compensation events  
- reversal events  
- корректирующие бизнес-процессы  
- четкие правила идемпотентности  
  
---  
  
#### 7. Конкурентные изменения  
Несколько процессов могут пытаться писать в один поток событий одновременно.  
  
**Решения:**  
- optimistic concurrency control  
- expected version check  
- sequence number / revision  
- retries  
  
---  
  
#### 8. Сложнее запросы и аналитика  
Сырые события неудобны для обычных бизнес-запросов.  
  
**Решения:**  
- проекции  
- read side БД  
- отдельное хранилище для аналитики  
- ETL/stream processing  
  
---  
  
#### 9. Не всегда нужен  
Для простого CRUD-приложения это может быть неоправданно сложно.  
  
**Решение:**  
- использовать просто audit log  
- temporal tables  
- soft delete + history tables  
- event sourcing только в критичных bounded context  
  
---  
  
### Базовые паттерны рядом с Event Sourcing  
  
#### 1. Snapshotting  
Периодически сохранять готовое состояние агрегата, чтобы не проигрывать всю историю с нуля.  
  
#### 2. Projections  
Строить удобные представления для чтения из потока событий.  
  
#### 3. CQRS  
Разделять модель записи и модель чтения.  
  
#### 4. Optimistic locking  
Контролировать версии потоков событий.  
  
#### 5. Idempotency  
Чтобы повторная обработка события не ломала состояние.  
  
#### 6. Outbox pattern  
Если нужно надежно публиковать события наружу.  
  
---  
  
### Удаление в такой модели  
  
Вы упомянули “удаление”. В event sourcing физическое удаление часто заменяется событием:  
  
- `EntityDeleted`  
- `UserArchived`  
- `OrderCancelled`  
  
То есть сущность считается удаленной логически, но история остается.  
  
Если нужно настоящее удаление:  
- это уже отдельная задача комплаенса/безопасности/retention policy  
- часто решается не на уровне бизнес-события, а на уровне политики хранения данных  
  
---  
  
### Простой пример  
  
События по заказу:  
  
1. `OrderCreated`  
2. `ItemAdded`  
3. `ItemAdded`  
4. `ShippingAddressChanged`  
5. `OrderConfirmed`  
6. `OrderCancelled`  
  
Текущее состояние заказа — это результат последовательного применения этих событий.  
  
---  
  
### Когда лучше выбрать не Event Sourcing, а что-то проще  
  
Если вам нужно только:  
- знать, кто изменил запись  
- видеть старое и новое значение  
- восстанавливать прошлую версию иногда  
  
то часто достаточно:  
- audit tables  
- temporal tables  
- history tables через триггеры  
- soft delete  
  
Это сильно проще в эксплуатации.

### Практический совет  
  
Если вы только изучаете подход, начните не с “перевести всю БД на события”, а с одного bounded context, где история действительно важна.  
  
Хороший путь:  
1. Оставить обычную read-модель.  
2. Для одного типа сущностей сделать append-only event store.  
3. Добавить проекцию текущего состояния.  
4. Добавить snapshots при необходимости.  
5. Проверить, оправдывает ли сложность ценность.

### 🔍 Что такое Event Sourcing?  
  
В классическом подходе (например, в реляционных базах данных) ты хранишь **текущее состояние объекта**:  
  
```  
User(id=1, name="Alice", email="alice@example.com")  
```  
  
А в Event Sourcing ты хранить **события**, которые привели к этому состоянию:  
  
```  
UserCreated(id=1, name="Alice", email="alice@example.com", timestamp=...)  
UserEmailChanged(id=1, new_email="alice.new@example.com", timestamp=...)  
```  
  
Таким образом, текущее состояние объекта может быть восстановлено путём применения всех событий в нужном порядке.  
  
---  
  
### 🧠 Преимущества Event Sourcing  
  
1. **Полная история изменений** — можно понять, как и почему что-то изменилось.  
2. **Восстановление данных** — легко восстановить состояние на любой момент времени.  
3. **Audit trail** — удобно для отчетности, логирования, соблюдения норм (например, GDPR).  
4. **Масштабируемость** — события могут быть обрабатываться параллельно.  
5. **Интеграция с CQRS** — часто используется совместно с Command Query Responsibility Segregation.  
  
---  
  
### ⚠️ Проблемы и ограничения  
  
1. **Сложность запросов** — если нужно быстро получить текущее состояние, нужно "проигрывать" все события.  
2. **Хранение большого количества данных** — события могут быть многочисленными.  
3. **Сложность в реализации** — требует более глубокого понимания архитектуры.  
4. **Не все данные подойдут** — например, временные или промежуточные данные лучше не хранить как события.  
5. **Нужно проектировать события аккуратно** — они должны быть **immutable**, **логически полные**, и хорошо структурированы.
