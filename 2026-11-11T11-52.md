#eventsourcing 
Я хочу написать приложение с распределённым хранением данных: т.е. есть сервер, и есть клиенты; при отсутствии интернета клиентское приложение позволяет работать с данными, которые хранятся на его стороне и при появлении интернета выполняет синхронизацию: затягивает все изменения, которые произошли за время отсутствия интернета на сервере и отправляет на сервер все изменения сделанные локально

Расскажи, насколько будет удобно для такого приложения применить подход eventsourcing? Какие есть подходы к выявлению и решению конфликтов в данных (когда одни и те же данные получили разные правки на сервере и на клиенте)

## ChatGPT 5.4  
Event sourcing для офлайн‑first / occasionally connected приложения — в целом очень естественный подход. Особенно если у вас есть:  
  
- локальные изменения на клиенте,  
- необходимость потом “дослать” их на сервер,  
- желание понимать, кто и что поменял,  
- потребность в разруливании конфликтов.  
  
Но он не является бесплатным: добавляет сложность модели, синхронизации и чтения данных. Ниже разберу, где он хорошо подходит, где нет, и как обычно решают конфликты.  
  
---  
  
### 1. Почему event sourcing вообще подходит для такой задачи  
  
В вашем сценарии клиент и сервер независимо накапливают изменения, а потом должны обменяться ими.  
  
В обычной CRUD-модели вы храните только текущее состояние:  
- было поле `status = draft`,  
- стало `status = approved`.  
  
При синхронизации вы видите только итог, но не всегда понимаете:  
- что именно менялось,  
- в каком порядке,  
- можно ли безопасно “слить” изменения,  
- где реальный конфликт, а где изменения не пересекаются.  
  
В event sourcing вместо хранения только текущего состояния вы храните последовательность событий:  
  
- `DocumentCreated`  
- `TitleChanged`  
- `StatusChanged`  
- `CommentAdded`  
  
Тогда синхронизация превращается в обмен событиями:  
- клиент отправляет события, которые накопил офлайн,  
- сервер отдает события, произошедшие, пока клиент был офлайн.  
  
Это очень похоже на “нативную” механику для распределенной системы.  
  
---  
  
### 2. Главные плюсы event sourcing в офлайн-синхронизации  
  
#### 2.1. Естественная модель синхронизации  
Вы синхронизируете не снимки состояния, а журнал изменений.  
  
Это удобно, потому что:  
- проще передавать только дельту,  
- проще восстанавливать порядок изменений,  
- проще делать повторную доставку,  
- проще обеспечивать идемпотентность.  
  
---  
  
#### 2.2. История изменений встроена сразу  
Для конфликтов очень полезно видеть не только “что есть сейчас”, но и “как к этому пришли”.  
  
Например:  
- клиент поменял название,  
- сервер поменял описание.  
  
Если это два разных события над разными полями, их можно объединить автоматически.  
  
---  
  
#### 2.3. Можно строить разные стратегии разрешения конфликтов  
События дают более высокий уровень семантики, чем просто “объект целиком перезаписан”.  
  
Разница между:  
- `UserRenamed("A")`  
- `UserRenamed("B")`  
  
и  
- “вот новый JSON пользователя целиком”  
  
огромная. В первом случае вы понимаете смысл операции.  
  
---  
  
#### 2.4. Удобно делать аудит, откат, повторное воспроизведение  
Для бизнес-систем это часто большой плюс:  
- кто изменил,  
- когда,  
- откуда,  
- что именно.  
  
---  
  
### 3. Минусы и ограничения event sourcing  
  
#### 3.1. Сложность сильно выше, чем у обычного CRUD  
Нужно проектировать:  
- события,  
- версии агрегатов,  
- репликацию,  
- обработку дублей,  
- порядок применения,  
- проекции для чтения.  
  
Если приложение относительно простое, можно “переплатить” архитектурой.  
  
---  
  
#### 3.2. Конфликты не исчезают  
Event sourcing **не решает конфликты сам по себе**. Он только дает лучший материал для их обнаружения и разруливания.  
  
Если клиент и сервер оба офлайн/онлайн изменили один и тот же бизнес-объект несовместимым образом — конфликт все равно останется.  
  
---  
  
#### 3.3. Чтение требует проекций  
Данные придется читать не из event log напрямую, а через:  
- snapshots,  
- materialized views / read models,  
- локальные проекции на клиенте.  
  
И на сервере, и на клиенте это дополнительный слой.  
  
---  
  
#### 3.4. Эволюция схем событий  
События живут долго. Меняются требования — нужно поддерживать:  
- versioning событий,  
- upcasting,  
- совместимость старых клиентов.  
  
Для офлайн-клиентов это особенно важно: старый клиент может прислать события старого формата спустя долгое время.  
  
---  
  
### 4. Когда event sourcing для такой задачи особенно уместен  
  
Подход хорош, если:  
  
- важна история изменений;  
- бизнес-операции значимее, чем просто “сохранить объект”;  
- есть сложные конфликты;  
- надо синхронизировать изменения между несколькими участниками;  
- полезно переигрывать изменения и восстанавливать состояние;  
- предметная область допускает моделирование через события.  
  
Примеры:  
- документы, заявки, задачи, заказы;  
- совместное редактирование бизнес-сущностей;  
- мобильные приложения с офлайн-режимом;  
- field service / выездные сотрудники / склад / продажи.  
  
---  
  
### 5. Когда лучше не начинать с event sourcing  
  
Если у вас:  
- простые данные,  
- редкие конфликты,  
- мало пользователей,  
- нет строгой необходимости в истории,  
- достаточно “последняя запись победила” или “ручное подтверждение конфликта”,  
  
то может быть проще использовать:  
- обычную БД,  
- version/timestamp на запись,  
- change log / outbox,  
- sync на уровне измененных сущностей.  
  
То есть не обязательно полный event sourcing. Иногда хватает:  
- хранения текущего состояния,  
- плюс журнала изменений для синхронизации.  
  
Это часто более практичный компромисс.  
  
---  
  
### 6. Базовая архитектура офлайн-синхронизации с event sourcing  
  
Обычно схема такая:  
  
#### На клиенте  
- локальное хранилище состояния;  
- локальный event log / очередь исходящих событий;  
- локальная проекция состояния;  
- механизм sync.  
  
#### На сервере  
- основной event store;  
- обработчики команд;  
- проекции/представления;  
- endpoint синхронизации.  
  
#### Поток работы  
1. Пользователь меняет данные на клиенте.  
2. Клиент создает событие локально.  
3. Событие применяется к локальной модели.  
4. Событие кладется в очередь на отправку.  
5. Когда сеть появилась — клиент отправляет события на сервер.  
6. Сервер валидирует и пытается применить их к актуальной версии агрегата.  
7. Сервер возвращает:  
   - подтверждение,  
   - либо конфликт,  
   - плюс события сервера, которых клиент еще не видел.  
8. Клиент подтягивает удаленные события и перестраивает/обновляет локальную проекцию.  
  
---  
  
### 7. Ключевая идея: синхронизировать не “всё подряд”, а потоки изменений  
  
Очень полезно мыслить в терминах:  
- **aggregate stream** — поток событий по одной сущности,  
- **global stream** — общий журнал всех событий,  
- **client cursor** — до какого места глобального журнала клиент дочитал.  
  
Тогда клиент хранит:  
- `lastServerEventPosition` — какую позицию сервера он уже синхронизировал,  
- `pendingLocalEvents` — какие локальные события еще не подтверждены сервером.  
  
---  
  
### 8. Как выявлять конфликты  
  
Конфликт — это не просто “данные разные”. Конфликт — это ситуация, когда изменения **невозможно автоматически совместить без потери бизнес-смысла**.  
  
Есть несколько уровней выявления.  
  
---  
  
#### 8.1. Optimistic concurrency по версии агрегата  
Самый базовый вариант.  
  
У каждой сущности есть версия:  
- клиент редактировал объект на версии 10;  
- пока он был офлайн, сервер довел объект до версии 12;  
- клиент пытается прислать событие “ожидаю версию 10”.  
  
Если сервер видит, что текущая версия уже 12 — значит, база для изменения устарела.  
  
Это еще не всегда конфликт, но уже сигнал: надо проверять, можно ли переиграть событие поверх новых данных.  
  
Это стандартный и очень полезный механизм.  
  
---  
  
#### 8.2. Проверка пересечения измененных полей  
Если у вас события семантические и/или можно выделить affected fields, то можно определить:  
  
- сервер изменил поле `description`,  
- клиент изменил поле `title`.  
  
Конфликта может не быть, изменения можно объединить.  
  
А если:  
- сервер поменял `status` на `Approved`,  
- клиент поменял `status` на `Draft`,  
  
то это уже явный конфликт по одному и тому же атрибуту.  
  
---  
  
#### 8.3. Проверка бизнес-инвариантов  
Даже если поля разные, может быть бизнес-конфликт.  
  
Пример:  
- клиент офлайн уменьшил остаток на складе;  
- сервер за это время тоже списал товар;  
- по отдельности события корректны,  
- вместе остаток ушел в минус.  
  
То есть конфликт обнаруживается не по полям, а по нарушению инварианта.  
  
---  
  
#### 8.4. Семантический конфликт на уровне операций  
Иногда важны не поля, а смысл команд.  
  
Например:  
- клиент: `CancelOrder`  
- сервер: `ShipOrder`  
  
Это конфликт даже если в хранилище меняются разные поля.  
  
Поэтому лучше синхронизировать именно **доменные события/команды**, а не сырые JSON-диффы.  
  
---  
  
### 9. Подходы к разрешению конфликтов  
  
Теперь главное: что делать, когда конфликт найден.  
  
---  
  
#### Подход 1. Last write wins (LWW)  
Самый простой:  
- побеждает более позднее изменение по timestamp/logical clock.  
  
##### Плюсы  
- просто реализовать;  
- подходит для неважных полей.  
  
##### Минусы  
- можно тихо потерять данные;  
- плохо подходит для бизнес-критичных данных.  
  
Используйте только там, где потеря приемлема:  
- UI-настройки,  
- некритичные метаданные,  
- кэшируемые предпочтения.  
  
---  
  
#### Подход 2. Версионный отказ + ручное разрешение  
Сервер говорит:  
- “твое изменение основано на старой версии”,  
- “автоматически применить нельзя”.  
  
Потом:  
- клиент показывает пользователю конфликт,  
- дает выбрать:  
  - оставить серверную версию,  
  - перезаписать локальной,  
  - слить вручную.  
  
##### Плюсы  
- надежно;  
- не теряет смысл.  
  
##### Минусы  
- плохой UX, если конфликтов много;  
- требует интерфейса разрешения конфликтов.  
  
Это хороший дефолт для важных сущностей.  
  
---  
  
#### Подход 3. Автоматическое слияние непересекающихся изменений  
Если клиент и сервер меняли разные поля/части объекта:  
- сливаем автоматически.  
  
Например:  
- клиент изменил `phone`,  
- сервер изменил `address`.  
  
Очень частый и практичный вариант.  
  
Но нужно четко знать, какие части действительно независимы.  
  
---  
  
#### Подход 4. Domain-specific merge  
Самый сильный вариант — заложить правила на уровне домена.  
  
Например:  
- для списка тегов — объединять множества;  
- для счетчиков — суммировать инкременты;  
- для комментариев — просто добавлять оба;  
- для статусов — использовать state machine и приоритеты;  
- для календаря — пытаться переставить слот или требовать подтверждение.  
  
Это лучший подход, если сущности важные и сценарии известны.  
  
---  
  
#### Подход 5. Rebase локальных изменений  
Очень полезный механизм.  
  
Идея:  
1. Клиент сделал локальные события поверх версии 10.  
2. Сервер за это время ушел на версию 12.  
3. Клиент получает события 11–12 с сервера.  
4. Применяет их к локальной базе.  
5. Затем пытается **повторно наложить** свои локальные неподтвержденные события поверх нового состояния.  
  
Это как git rebase.  
  
Если после replay локальное событие все еще валидно — отлично.  
Если нет — конфликт.  
  
Это один из самых естественных механизмов для event sourcing.  
  
---  
  
#### Подход 6. CRDT  
Если типы данных подходят, можно использовать CRDT — структуры данных, которые автоматически сходятся без центрального разрешения конфликтов.  
  
Примеры:  
- grow-only set,  
- observed-remove set,  
- counter,  
- некоторые виды текстовых структур.  
  
##### Плюсы  
- сильная математическая гарантия сходимости;  
- отлично для highly distributed систем.  
  
##### Минусы  
- сложно;  
- не все бизнес-сущности можно представить как CRDT;  
- инварианты типа “не уходить в отрицательный баланс” CRDT сами по себе не решают.  
  
CRDT хороши для:  
- совместного редактирования,  
- множеств,  
- реакций,  
- счетчиков,  
- presence/курсоров/состояний UI.  
  
Но не как универсальная замена доменной логики.  
  
---  
  
### 10. Практическая стратегия: где какой тип разрешения конфликтов применять  
  
На практике обычно делают **не один универсальный способ**, а набор правил по типам данных.  
  
Например:  
  
- текстовые заметки → трехсторонний merge или ручной конфликт;  
- список комментариев → append-only, без конфликта;  
- теги → set-union;  
- статус документа → доменное правило или ручной конфликт;  
- счетчики → инкрементные события;  
- остатки / финансы → строгая серверная валидация, конфликт вручную или через compensating action.  
  
Это важная мысль: **конфликт — свойство не технологии, а доменной модели**.  
  
---  
  
### 11. Как проектировать события, чтобыты решались проще  
  
Очень важный момент: удобство синхронизации зависит от формы событий.  
  
#### Плохо  
- `EntityUpdated(newFullStateJson)`  
  
Такое событие грубое. По нему трудно понять смысл изменений.  
  
#### Лучше  
- `NameChanged`  
- `AddressChanged`  
- `LineItemAdded`  
- `LineItemRemoved`  
- `QuantityAdjusted`  
- `CommentAdded`  
  
Семантические события:  
- проще валидировать,  
- проще мерджить,  
- проще показывать пользователю конфликт,  
- проще делать selective retry.  
  
---  
  
### 12. Как уменьшить число конфликтов архитектурно  
  
Не только “разруливать”, но и “не создавать”.  
  
#### 12.1. Дробить агрегаты правильно  
Если одна сущность слишком большая, много пользователей будут конфликтовать о неё.  
  
Лучше разделить:  
- документ отдельно,  
- комментарии отдельно,  
- вложения отдельно,  
- подэлементы отдельно.  
  
Чем меньше aggregate boundary, тем меньше ложных конфликтов.  
  
---  
  
#### 12.2. Делать операции append-only там, где можно  
Например:  
- комментарии,  
- сообщения,  
- лог действий.  
  
Append-only почти не конфликтуют.  
  
---  
  
#### 12.3. Хранить изменения как операции, а не как полные снимки  
Например:  
- не “новый список тегов полностью”,  
- а “добавить тег X”, “убрать тег Y”.  
  
Это уменьшает вероятность конфликтов.  
  
---  
  
#### 12.4. Избегать редактирования одного и того же поля многими участниками  
Иногда можно изменить UX:  
- блокировки,  
- “кто сейчас редактирует”,  
- предупреждения,  
- короткие сессии редактирования.  
  
Даже мягкие UX-механизмы сильно уменьшают число конфликтов.  
  
---  
  
### 13. Сервер должен быть источником истины?  
Обычно да.  
  
Для большинства бизнес-приложений хорошая модель такая:  
- клиент может оптимистично принимать локальные изменения;  
- но окончательное подтверждение и canonical ordering — на сервере.  
  
Почему это важно:  
- сервер может проверить инварианты;  
- сервер может назначить окончательные номера/позиции;  
- сервер может определить глобальный порядок.  
  
При этом клиент может работать автономно, но должен быть готов, что после синка:  
- какие-то события подтвердятся,  
- какие-то будут отклонены,  
- какие-то потребуют пересборки локального состояния.  
  
---  
  
### 14. Как технически организовать sync protocol  
  
Минимально полезный протокол обычно включает:  
  
#### От клиента на сервер  
- `clientId`  
- список локальных неподтвержденных событий  
- для каждого события:  
  - `eventId`  
  - `aggregateId`  
  - `expectedVersion`  
  - `eventType`  
  - `payload`  
  - `localTimestamp`  
- `lastKnownServerPosition`  
  
#### От сервера клиенту  
- подтвержденные `eventId`  
- список отклоненных событий с причиной  
- список конфликтов  
- новые серверные события после `lastKnownServerPosition`  
- новый `serverPosition`  
  
---  
  
### 15. Идемпотентность обязательна  
  
В офлайн-синхронизации сеть ненадежна:  
- запрос мог дойти, а ответ потеряться;  
- клиент может повторить отправку.  
  
Поэтому каждое событие должно иметь устойчивый `eventId`, а сервер должен уметь говорить:  
- “это событие я уже применял”.  
  
Без идемпотентности вы получите дубли.  
  
---  
  
### 16. Порядок событий и причинность  
  
Если клиент локально сделал:  
1. `ItemAdded`  
2. `QuantityChanged`  
  
то на сервер они должны примениться в том же причинном порядке.  
  
Поэтому:  
- либо события внутри aggregate stream упорядочены строго,  
- либо вы явно храните parent/causation/correlation metadata.  
  
Для простых систем достаточно последовательного номера в локальной очереди.  
  
---  
  
### 17. Нужны ли snapshots?  
Да, почти наверняка.  
  
И на клиенте, и на сервере чистый replay всех событий со временем станет слишком дорогим.  
  
Обычно делают:  
- event log как источник истины,  
- snapshots/проекции для быстрого чтения.  
  
На клиенте это особенно важно для UX.  
  
---  
  
### 18. Альтернатива: не полный event sourcing, а change tracking + versioning  
  
Очень часто это лучшее решение.  
  
Вместо полного ES:  
- храните текущее состояние сущностей;  
- ведите журнал локальных изменений;  
- каждой сущности дайте `version` / `updatedAt` / `etag`;  
- синхронизируйте changed entities или patch operations;  
- конфликты выявляйте по version или вручную.  
  
#### Плюсы  
- сильно проще;  
- подходит для большинства приложений.  
  
#### Минусы  
- меньше аудита;  
- слабее семантика;  
- сложнее делать replay и глубокий анализ конфликтов.  
  
Если вы только начинаете проект, это часто более разумный MVP.  
  
---  
  
### 19. Мой практический вывод: стоит ли брать event sourcing  
  
#### Да, если  
- приложение действительно офлайн-first;  
- важна надежная синхронизация изменений;  
- нужна история;  
- доменная модель нетривиальная;  
- команда готова к повышенной сложности.  
  
#### Скорее нет, если  
- приложение в целом CRUD;  
- конфликты редки;  
- история не критична;  
- команда не работала с ES;  
- нужен быстрый и простой запуск.

### 20. Рекомендованный компромисс

#### Вариант A: “ES-lite”

- изменения представляйте как операции/события;  
- локально копите очередь операций;  
- сервер применяет операции с optimistic concurrency;  
- есть журнал изменений для sync и аудита;  
- read model обычная CRUD/SQL.  
  
Это дает много плюсов ES, но без полного погружения.  
  
#### Вариант B: Полный event sourcing  
Используйте, если:  
- у вас зрелая архитектурная дисциплина;  
- есть четкие aggregate boundaries;  
- вы готовы проектировать replay, projections, upcasting, conflict resolution как first-class concerns.

### 21. Конкретная стратегия разрешения конфликтов, которую я бы рекомендовал  
  
Для большинства бизнес-приложений:  
  
1. **Optimistic concurrency по версии агрегата**    
Каждое локальное изменение отправляется с `expectedVersion`.  
  
2. **Rebase локальных неподтвержденных событий поверх новых серверных**    
Если база устарела — сначала подтягиваем серверные изменения, затем пробуем переиграть локальные.  
  
3. **Автоматический merge для непересекающихся изменений**    
Разные поля/подсущности — сливаем автоматически.  
  
4. **Domain-specific merge rules там, где это возможно**    
Для списков, тегов, комментариев, счетчиков, вложений.  
  
5. **Ручное разрешение для критичных бизнес-конфликтов**    
Статусы, финансовые операции, складские остатки, юридически значимые данные.  
  
6. **Идемпотентность + уникальные eventId**    
Обязательно.  
  
7. **Семантические события вместо “обновить весь объект”**    
Это резко упростит sync и конфликты.

### 🔧 Что такое Event Sourcing?  
  
**Event Sourcing** — это паттерн, при котором состояние системы сохраняется не как текущее значение, а как последовательность событий (events), которые привели к этому состоянию. Например:  
  
```json  
{  
  "userId": "123",  "event": "UserCreated",  "timestamp": "2025-04-05T10:00:00Z",  "data": { "name": "Иван", "email": "ivan@example.com" }}  
```  
  
Каждое изменение — это событие. Состояние объекта восстанавливается путём применения всех событий в нужном порядке.  
  
---  
  
### 🔄 Подходит ли Event Sourcing для твоего случая?  
  
Да, **Event Sourcing может быть хорошим выбором**, особенно если ты хочешь:  
  
- Иметь полную историю изменений.  
- Упростить синхронизацию: можно просто передавать события.  
- Легко обрабатывать конфликты (например, через merge-логику).  
- Поддерживать сложные сценарии, где важно знать **как изменилось** состояние, а не только **что стало**.  
  
#### ✅ Преимущества:  
- **Прозрачность**: можно видеть, как всё происходило.  
- **Легко восстанавливать состояние**.  
- **Удобно синхронизировать**: передаётся не только изменённое, но и история.  
- **Можно строить сложные правила обработки конфликтов**.  
  
#### ❗ Недостатки:  
- Сложнее для простых сценариев.  
- Требуется дополнительная логика восстановления состояния.  
- Не всегда удобно работать с "текущими" значениями (нужно пересчитывать).  
  
---  
  
### 📦 Как организовать распределённое хранение данных?  
  
Представим, что у тебя есть:  
  
- **Сервер** — центральное хранилище, где хранятся события.  
- **Клиенты** — локальные хранилища, которые могут работать офлайн и записывать события локально.  
- При подключении — происходит синхронизация.  
  
#### Архитектура примерно такая:  
  
##### 1. Локальное хранилище клиента:  
- Хранит события локально.  
- Ведёт счётчик последнего обработанного события (например, `lastSyncedEventId`).  
  
##### 2. Сервер:  
- Хранит поток событий по сущностям (например, `user/123/events`).  
- Ведёт `lastEventId` для каждого пользователя или ресурса.  
  
##### 3. Синхронизация:  
- Клиент присылает свои события (с `lastSyncedEventId`).  
- Сервер проверяет, нет ли конфликтов (если они есть — решает).  
- Сервер отдаёт клиенту новые события, которые он ещё не видел.  
- Обновляется `lastSyncedEventId`.  
  
---  
  
### ⚔️ Как решать конфликты?  
  
В распределённых системах конфликты возникают, когда одно и то же состояние изменено на клиенте и сервере независимо.  
  
#### Возможные стратегии решения конфликтов:  
  
##### 1. **Last Write Wins (LWW)** — самый простой способ:  
- Просто берётся последнее событие по времени.  
- Минус: теряется информация о том, кто что делал.  
  
##### 2. **Merge Events (ручной или автоматический)**  
- События объединяются логически.  
- Например: два клиента обновили поля `name` и `email` — можно сделать merge.  
- Требует логики для понимания семантики событий.  
  
##### 3. **Conflict Resolution Service**  
- Специальный сервис, который решает конфликты.  
- Может использовать бизнес-правила (например, "если имя было изменено на сервере, то локальное изменение игнорируется").  
  
##### 4. **Version-based Conflict Detection**  
- Каждое событие имеет версию (`version`, `sequence`, `timestamp`).  
- Если версия на сервере больше — клиент должен принять изменения сервера.  
- Если версии совпадают — можно считать, что всё ок.  
- Если клиент имеет более новую версию — сервер может отклонить её и потребовать синхронизации.  
  
##### 5. **CRDT (Conflict-free Replicated Data Types)**  
- Это продвинутый подход, где данные могут быть синхронизированы без конфликтов.  
- Но он сложнее и требует специального дизайна структур данных.  
  
---  
  
### 🧠 Какие вопросы стоит задать себе?  
  
1. **Какие типы данных меняются?** (например, пользовательские записи, документы)  
2. **Насколько часто будут возникать конфликты?**  
3. **Нужна ли полная история изменений или достаточно текущего состояния?**  
4. **Будет ли клиент работать офлайн долгое время?**  
5. **Какие действия будут происходить в офлайн-режиме?**

### 1. Почему event sourcing вообще подходит для такой задачи  
  
В вашем сценарии клиент и сервер независимо накапливают изменения, а потом должны обменяться ими.  
  
В обычной CRUD-модели вы храните только текущее состояние:  
- было поле `status = draft`,  
- стало `status = approved`.  
  
При синхронизации вы видите только итог, но не всегда понимаете:  
- что именно менялось,  
- в каком порядке,  
- можно ли безопасно “слить” изменения,  
- где реальный конфликт, а где изменения не пересекаются.  
  
В event sourcing вместо хранения только текущего состояния вы храните последовательность событий:  
  
- `DocumentCreated`  
- `TitleChanged`  
- `StatusChanged`  
- `CommentAdded`  
  
Тогда синхронизация превращается в обмен событиями:  
- клиент отправляет события, которые накопил офлайн,  
- сервер отдает события, произошедшие, пока клиент был офлайн.  
  
Это очень похоже на “нативную” механику для распределенной системы.  
  
---  
  
### 2. Главные плюсы event sourcing в офлайн-синхронизации  
  
#### 2.1. Естественная модель синхронизации  
Вы синхронизируете не снимки состояния, а журнал изменений.  
  
Это удобно, потому что:  
- проще передавать только дельту,  
- проще восстанавливать порядок изменений,  
- проще делать повторную доставку,  
- проще обеспечивать идемпотентность.  
  
---  
  
#### 2.2. История изменений встроена сразу  
Для конфликтов очень полезно видеть не только “что есть сейчас”, но и “как к этому пришли”.  
  
Например:  
- клиент поменял название,  
- сервер поменял описание.  
  
Если это два разных события над разными полями, их можно объединить автоматически.  
  
---  
  
#### 2.3. Можно строить разные стратегии разрешения конфликтов  
События дают более высокий уровень семантики, чем просто “объект целиком перезаписан”.  
  
Разница между:  
- `UserRenamed("A")`  
- `UserRenamed("B")`  
  
и  
- “вот новый JSON пользователя целиком”  
  
огромная. В первом случае вы понимаете смысл операции.  
  
---  
  
#### 2.4. Удобно делать аудит, откат, повторное воспроизведение  
Для бизнес-систем это часто большой плюс:  
- кто изменил,  
- когда,  
- откуда,  
- что именно.  
  
---  
  
### 3. Минусы и ограничения event sourcing  
  
#### 3.1. Сложность сильно выше, чем у обычного CRUD  
Нужно проектировать:  
- события,  
- версии агрегатов,  
- репликацию,  
- обработку дублей,  
- порядок применения,  
- проекции для чтения.  
  
Если приложение относительно простое, можно “переплатить” архитектурой.  
  
---  
  
#### 3.2. Конфликты не исчезают  
Event sourcing **не решает конфликты сам по себе**. Он только дает лучший материал для их обнаружения и разруливания.  
  
Если клиент и сервер оба офлайн/онлайн изменили один и тот же бизнес-объект несовместимым образом — конфликт все равно останется.  
  
---  
  
#### 3.3. Чтение требует проекций  
Данные придется читать не из event log напрямую, а через:  
- snapshots,  
- materialized views / read models,  
- локальные проекции на клиенте.  
  
И на сервере, и на клиенте это дополнительный слой.  
  
---  
  
#### 3.4. Эволюция схем событий  
События живут долго. Меняются требования — нужно поддерживать:  
- versioning событий,  
- upcasting,  
- совместимость старых клиентов.  
  
Для офлайн-клиентов это особенно важно: старый клиент может прислать события старого формата спустя долгое время.  
  
---  
  
### 4. Когда event sourcing для такой задачи особенно уместен  
  
Подход хорош, если:  
  
- важна история изменений;  
- бизнес-операции значимее, чем просто “сохранить объект”;  
- есть сложные конфликты;  
- надо синхронизировать изменения между несколькими участниками;  
- полезно переигрывать изменения и восстанавливать состояние;  
- предметная область допускает моделирование через события.  
  
Примеры:  
- документы, заявки, задачи, заказы;  
- совместное редактирование бизнес-сущностей;  
- мобильные приложения с офлайн-режимом;  
- field service / выездные сотрудники / склад / продажи.  
  
---  
  
### 5. Когда лучше не начинать с event sourcing  
  
Если у вас:  
- простые данные,  
- редкие конфликты,  
- мало пользователей,  
- нет строгой необходимости в истории,  
- достаточно “последняя запись победила” или “ручное подтверждение конфликта”,  
  
то может быть проще использовать:  
- обычную БД,  
- version/timestamp на запись,  
- change log / outbox,  
- sync на уровне измененных сущностей.  
  
То есть не обязательно полный event sourcing. Иногда хватает:  
- хранения текущего состояния,  
- плюс журнала изменений для синхронизации.  
  
Это часто более практичный компромисс.  
  
---  
  
### 6. Базовая архитектура офлайн-синхронизации с event sourcing  
  
Обычно схема такая:  
  
#### На клиенте  
- локальное хранилище состояния;  
- локальный event log / очередь исходящих событий;  
- локальная проекция состояния;  
- механизм sync.  
  
#### На сервере  
- основной event store;  
- обработчики команд;  
- проекции/представления;  
- endpoint синхронизации.  
  
#### Поток работы  
1. Пользователь меняет данные на клиенте.  
2. Клиент создает событие локально.  
3. Событие применяется к локальной модели.  
4. Событие кладется в очередь на отправку.  
5. Когда сеть появилась — клиент отправляет события на сервер.  
6. Сервер валидирует и пытается применить их к актуальной версии агрегата.  
7. Сервер возвращает:  
   - подтверждение,  
   - либо конфликт,  
   - плюс события сервера, которых клиент еще не видел.  
8. Клиент подтягивает удаленные события и перестраивает/обновляет локальную проекцию.  
  
---  
  
### 7. Ключевая идея: синхронизировать не “всё подряд”, а потоки изменений  
  
Очень полезно мыслить в терминах:  
- **aggregate stream** — поток событий по одной сущности,  
- **global stream** — общий журнал всех событий,  
- **client cursor** — до какого места глобального журнала клиент дочитал.  
  
Тогда клиент хранит:  
- `lastServerEventPosition` — какую позицию сервера он уже синхронизировал,  
- `pendingLocalEvents` — какие локальные события еще не подтверждены сервером.  
  
---  
  
### 8. Как выявлять конфликты  
  
Конфликт — это не просто “данные разные”. Конфликт — это ситуация, когда изменения **невозможно автоматически совместить без потери бизнес-смысла**.  
  
Есть несколько уровней выявления.  
  
---  
  
#### 8.1. Optimistic concurrency по версии агрегата  
Самый базовый вариант.  
  
У каждой сущности есть версия:  
- клиент редактировал объект на версии 10;  
- пока он был офлайн, сервер довел объект до версии 12;  
- клиент пытается прислать событие “ожидаю версию 10”.  
  
Если сервер видит, что текущая версия уже 12 — значит, база для изменения устарела.  
  
Это еще не всегда конфликт, но уже сигнал: надо проверять, можно ли переиграть событие поверх новых данных.  
  
Это стандартный и очень полезный механизм.  
  
---  
  
#### 8.2. Проверка пересечения измененных полей  
Если у вас события семантические и/или можно выделить affected fields, то можно определить:  
  
- сервер изменил поле `description`,  
- клиент изменил поле `title`.  
  
Конфликта может не быть, изменения можно объединить.  
  
А если:  
- сервер поменял `status` на `Approved`,  
- клиент поменял `status` на `Draft`,  
  
то это уже явный конфликт по одному и тому же атрибуту.  
  
---  
  
#### 8.3. Проверка бизнес-инвариантов  
Даже если поля разные, может быть бизнес-конфликт.  
  
Пример:  
- клиент офлайн уменьшил остаток на складе;  
- сервер за это время тоже списал товар;  
- по отдельности события корректны,  
- вместе остаток ушел в минус.  
  
То есть конфликт обнаруживается не по полям, а по нарушению инварианта.  
  
---  
  
#### 8.4. Семантический конфликт на уровне операций  
Иногда важны не поля, а смысл команд.  
  
Например:  
- клиент: `CancelOrder`  
- сервер: `ShipOrder`  
  
Это конфликт даже если в хранилище меняются разные поля.  
  
Поэтому лучше синхронизировать именно **доменные события/команды**, а не сырые JSON-диффы.  
  
---  
  
### 9. Подходы к разрешению конфликтов  
  
Теперь главное: что делать, когда конфликт найден.  
  
---  
  
#### Подход 1. Last write wins (LWW)  
Самый простой:  
- побеждает более позднее изменение по timestamp/logical clock.  
  
##### Плюсы  
- просто реализовать;  
- подходит для неважных полей.  
  
##### Минусы  
- можно тихо потерять данные;  
- плохо подходит для бизнес-критичных данных.  
  
Используйте только там, где потеря приемлема:  
- UI-настройки,  
- некритичные метаданные,  
- кэшируемые предпочтения.  
  
---  
  
#### Подход 2. Версионный отказ + ручное разрешение  
Сервер говорит:  
- “твое изменение основано на старой версии”,  
- “автоматически применить нельзя”.  
  
Потом:  
- клиент показывает пользователю конфликт,  
- дает выбрать:  
  - оставить серверную версию,  
  - перезаписать локальной,  
  - слить вручную.  
  
##### Плюсы  
- надежно;  
- не теряет смысл.  
  
##### Минусы  
- плохой UX, если конфликтов много;  
- требует интерфейса разрешения конфликтов.  
  
Это хороший дефолт для важных сущностей.  
  
---  
  
#### Подход 3. Автоматическое слияние непересекающихся изменений  
Если клиент и сервер меняли разные поля/части объекта:  
- сливаем автоматически.  
  
Например:  
- клиент изменил `phone`,  
- сервер изменил `address`.  
  
Очень частый и практичный вариант.  
  
Но нужно четко знать, какие части действительно независимы.  
  
---  
  
#### Подход 4. Domain-specific merge  
Самый сильный вариант — заложить правила на уровне домена.  
  
Например:  
- для списка тегов — объединять множества;  
- для счетчиков — суммировать инкременты;  
- для комментариев — просто добавлять оба;  
- для статусов — использовать state machine и приоритеты;  
- для календаря — пытаться переставить слот или требовать подтверждение.  
  
Это лучший подход, если сущности важные и сценарии известны.  
  
---  
  
#### Подход 5. Rebase локальных изменений  
Очень полезный механизм.  
  
Идея:  
1. Клиент сделал локальные события поверх версии 10.  
2. Сервер за это время ушел на версию 12.  
3. Клиент получает события 11–12 с сервера.  
4. Применяет их к локальной базе.  
5. Затем пытается **повторно наложить** свои локальные неподтвержденные события поверх нового состояния.  
  
Это как git rebase.  
  
Если после replay локальное событие все еще валидно — отлично.  
Если нет — конфликт.  
  
Это один из самых естественных механизмов для event sourcing.  
  
---  
  
#### Подход 6. CRDT  
Если типы данных подходят, можно использовать CRDT — структуры данных, которые автоматически сходятся без центрального разрешения конфликтов.  
  
Примеры:  
- grow-only set,  
- observed-remove set,  
- counter,  
- некоторые виды текстовых структур.  
  
##### Плюсы  
- сильная математическая гарантия сходимости;  
- отлично для highly distributed систем.  
  
##### Минусы  
- сложно;  
- не все бизнес-сущности можно представить как CRDT;  
- инварианты типа “не уходить в отрицательный баланс” CRDT сами по себе не решают.  
  
CRDT хороши для:  
- совместного редактирования,  
- множеств,  
- реакций,  
- счетчиков,  
- presence/курсоров/состояний UI.  
  
Но не как универсальная замена доменной логики.  
  
---  
  
### 10. Практическая стратегия: где какой тип разрешения конфликтов применять  
  
На практике обычно делают **не один универсальный способ**, а набор правил по типам данных.  
  
Например:  
  
- текстовые заметки → трехсторонний merge или ручной конфликт;  
- список комментариев → append-only, без конфликта;  
- теги → set-union;  
- статус документа → доменное правило или ручной конфликт;  
- счетчики → инкрементные события;  
- остатки / финансы → строгая серверная валидация, конфликт вручную или через compensating action.  
  
Это важная мысль: **конфликт — свойство не технологии, а доменной модели**.  
  
---  
  
### 11. Как проектировать события, чтобыты решались проще  
  
Очень важный момент: удобство синхронизации зависит от формы событий.  
  
#### Плохо  
- `EntityUpdated(newFullStateJson)`  
  
Такое событие грубое. По нему трудно понять смысл изменений.  
  
#### Лучше  
- `NameChanged`  
- `AddressChanged`  
- `LineItemAdded`  
- `LineItemRemoved`  
- `QuantityAdjusted`  
- `CommentAdded`  
  
Семантические события:  
- проще валидировать,  
- проще мерджить,  
- проще показывать пользователю конфликт,  
- проще делать selective retry.  
  
---  
  
### 12. Как уменьшить число конфликтов архитектурно  
  
Не только “разруливать”, но и “не создавать”.  
  
#### 12.1. Дробить агрегаты правильно  
Если одна сущность слишком большая, много пользователей будут конфликтовать о неё.  
  
Лучше разделить:  
- документ отдельно,  
- комментарии отдельно,  
- вложения отдельно,  
- подэлементы отдельно.  
  
Чем меньше aggregate boundary, тем меньше ложных конфликтов.  
  
---  
  
#### 12.2. Делать операции append-only там, где можно  
Например:  
- комментарии,  
- сообщения,  
- лог действий.  
  
Append-only почти не конфликтуют.  
  
---  
  
#### 12.3. Хранить изменения как операции, а не как полные снимки  
Например:  
- не “новый список тегов полностью”,  
- а “добавить тег X”, “убрать тег Y”.  
  
Это уменьшает вероятность конфликтов.  
  
---  
  
#### 12.4. Избегать редактирования одного и того же поля многими участниками  
Иногда можно изменить UX:  
- блокировки,  
- “кто сейчас редактирует”,  
- предупреждения,  
- короткие сессии редактирования.  
  
Даже мягкие UX-механизмы сильно уменьшают число конфликтов.  
  
---  
  
### 13. Сервер должен быть источником истины?  
Обычно да.  
  
Для большинства бизнес-приложений хорошая модель такая:  
- клиент может оптимистично принимать локальные изменения;  
- но окончательное подтверждение и canonical ordering — на сервере.  
  
Почему это важно:  
- сервер может проверить инварианты;  
- сервер может назначить окончательные номера/позиции;  
- сервер может определить глобальный порядок.  
  
При этом клиент может работать автономно, но должен быть готов, что после синка:  
- какие-то события подтвердятся,  
- какие-то будут отклонены,  
- какие-то потребуют пересборки локального состояния.  
  
---  
  
### 14. Как технически организовать sync protocol  
  
Минимально полезный протокол обычно включает:  
  
#### От клиента на сервер  
- `clientId`  
- список локальных неподтвержденных событий  
- для каждого события:  
  - `eventId`  
  - `aggregateId`  
  - `expectedVersion`  
  - `eventType`  
  - `payload`  
  - `localTimestamp`  
- `lastKnownServerPosition`  
  
#### От сервера клиенту  
- подтвержденные `eventId`  
- список отклоненных событий с причиной  
- список конфликтов  
- новые серверные события после `lastKnownServerPosition`  
- новый `serverPosition`  
  
---  
  
### 15. Идемпотентность обязательна  
  
В офлайн-синхронизации сеть ненадежна:  
- запрос мог дойти, а ответ потеряться;  
- клиент может повторить отправку.  
  
Поэтому каждое событие должно иметь устойчивый `eventId`, а сервер должен уметь говорить:  
- “это событие я уже применял”.  
  
Без идемпотентности вы получите дубли.  
  
---  
  
### 16. Порядок событий и причинность  
  
Если клиент локально сделал:  
1. `ItemAdded`  
2. `QuantityChanged`  
  
то на сервер они должны примениться в том же причинном порядке.  
  
Поэтому:  
- либо события внутри aggregate stream упорядочены строго,  
- либо вы явно храните parent/causation/correlation metadata.  
  
Для простых систем достаточно последовательного номера в локальной очереди.  
  
---  
  
### 17. Нужны ли snapshots?  
Да, почти наверняка.  
  
И на клиенте, и на сервере чистый replay всех событий со временем станет слишком дорогим.  
  
Обычно делают:  
- event log как источник истины,  
- snapshots/проекции для быстрого чтения.  
  
На клиенте это особенно важно для UX.  
  
---  
  
### 18. Альтернатива: не полный event sourcing, а change tracking + versioning  
  
Очень часто это лучшее решение.  
  
Вместо полного ES:  
- храните текущее состояние сущностей;  
- ведите журнал локальных изменений;  
- каждой сущности дайте `version` / `updatedAt` / `etag`;  
- синхронизируйте changed entities или patch operations;  
- конфликты выявляйте по version или вручную.  
  
#### Плюсы  
- сильно проще;  
- подходит для большинства приложений.  
  
#### Минусы  
- меньше аудита;  
- слабее семантика;  
- сложнее делать replay и глубокий анализ конфликтов.  
  
Если вы только начинаете проект, это часто более разумный MVP.  
  
---  
  
### 19. Мой практический вывод: стоит ли брать event sourcing  
  
#### Да, если  
- приложение действительно офлайн-first;  
- важна надежная синхронизация изменений;  
- нужна история;  
- доменная модель нетривиальная;  
- команда готова к повышенной сложности.  
  
#### Скорее нет, если  
- приложение в целом CRUD;  
- конфликты редки;  
- история не критична;  
- команда не работала с ES;  
- нужен быстрый и простой запуск.  
  
---  
  
### 20. Рекомендованный компромисс  
  
Я бы часто советовал такой путь:  
  
#### Вариант A: “ES-lite”  
- текущее состояние храните отдельно;  
- изменения представляйте как операции/события;  
- локально копите очередь операций;  
- сервер применяет операции с optimistic concurrency;  
- есть журнал изменений для sync и аудита;  
- read model обычная CRUD/SQL.  
  
Это дает много плюсов ES, но без полного погружения.  
  
#### Вариант B: Полный event sourcing  
Используйте, если:  
- у вас зрелая архитектурная дисциплина;  
- есть четкие aggregate boundaries;  
- вы готовы проектировать replay, projections, upcasting, conflict resolution как first-class concerns.  
  
---  
  
### 21. Конкретная стратегия разрешения конфликтов, которую я бы рекомендовал  
  
Для большинства бизнес-приложений:  
  
1. **Optimistic concurrency по версии агрегата**    
Каждое локальное изменение отправляется с `expectedVersion`.  
  
2. **Rebase локальных неподтвержденных событий поверх новых серверных**    
Если база устарела — сначала подтягиваем серверные изменения, затем пробуем переиграть локальные.  
  
3. **Автоматический merge для непересекающихся изменений**    
Разные поля/подсущности — сливаем автоматически.  
  
4. **Domain-specific merge rules там, где это возможно**    
Для списков, тегов, комментариев, счетчиков, вложений.  
  
5. **Ручное разрешение для критичных бизнес-конфликтов**    
Статусы, финансовые операции, складские остатки, юридически значимые данные.  
  
6. **Идемпотентность + уникальные eventId**    
Обязательно.  
  
7. **Семантические события вместо “обновить весь объект”**    
Это резко упростит sync и конфликты.

### 22. Если кратко  
  
#### Насколько удобно применять event sourcing?  
Удобно, если ваша главная задача — синхронизация изменений между офлайн-клиентами и сервером. Для этого ES концептуально очень подходит.  
  
#### В чем подвох?  
Он усложняет систему. Конфликты не убирает, а только делает их лучше наблюдаемыми и лучше управляемыми.  
  
#### Какие лучшие подходы к конфликтам?  
На практике:  
- optimistic concurrency,  
- rebase,  
- auto-merge для независимых изменений,  
- domain-specific merge,  
- manual resolution для критичных кейсов,  
- иногда CRDT для специальных типов данных.

## Perplexity  
Да, event sourcing **хорошо подходит** для offline-first приложения: локальные изменения удобно представлять как неизменяемые события в локальном журнале, а синхронизация сводится к обмену событиями, а не «последними версиями записей». Но event sourcing сам по себе не решает конфликты — он лишь делает их видимыми и даёт материал для детерминированного разрешения. [github](https://github.com/jasoncrawford/claude-skills/blob/main/offline-first-sync/SKILL.md)  
  
### Почему event sourcing уместен  
  
Клиент во время отсутствия сети пишет события в локальный append-only журнал: `OrderCreated`, `ItemAdded`, `FieldChanged`, `OrderConfirmed` и т. п. Параллельно он поддерживает локальную проекцию состояния — например, таблицу заказов, собранную из событий.  
  
При появлении сети:  
  
1. Клиент отправляет серверу только ещё не отправленные события (outbox).  
2. Сервер валидирует их, сохраняет и присваивает глобальный порядковый номер либо позицию в стриме.  
3. Клиент получает события, произошедшие на сервере после его последней известной позиции (cursor / checkpoint).  
4. Клиент применяет чужие события к локальному журналу и пересобирает проекции.  
  
Такой подход естественно поддерживает идемпотентность: каждое событие имеет UUID, а сервер игнорирует повторную доставку уже известного события. В описанных реализациях push передаёт локальные события с UUID, сервер вставляет их с защитой от дубликатов, а pull возвращает события после последнего виденного клиентом `seq`. [github](https://github.com/jasoncrawford/claude-skills/blob/main/offline-first-sync/SKILL.md)  
  
### Что это даёт  
  
| Аспект | Выгода event sourcing |  
|---|---|  
| Оффлайн-работа | Клиент продолжает записывать события и локально проецировать состояние без обращения к серверу.  [github](https://github.com/jasoncrawford/claude-skills/blob/main/offline-first-sync/SKILL.md) |  
| Аудит | Сохраняется история «кто, что и когда изменил», а не только итоговое значение. |  
| Отладка и восстановление | Состояние можно пересобрать из журнала; ошибки проекций исправляются перезапуском проекции. |  
| Конфликты | Видны на уровне намерений (`ItemAdded`, `StatusChanged`), а не только на уровне финального JSON. |  
| Расширение | Новые проекции, отчёты и интеграции можно строить из уже существующих событий. |  
  
Главный компромисс: вам придётся проектировать события как **бизнес-факты**, а не как отражение CRUD-операций. Иначе получится «event-sourced CRUD» — сложная инфраструктура без реальной пользы от журнала событий. ### Как выявлять конфликты  
  
Конфликт — это не просто «две разные версии записи». Это ситуация, когда два изменения **не имеют причинной связи**: ни сервер, ни клиент не видел изменение другого в момент создания своего.  
  
Практичная модель:  
  
- Каждое событие содержит: `eventId` (UUID), `aggregateId`, `eventType`, `payload`, `clientId`, `occurredAt`, `lamportClock` или vector clock.  
- Сервер хранит события в стриме агрегата с монотонным номером `sequence`.  
- Клиент хранит `lastSeenServerSequence` — границу известных ему серверных событий.  
- Если клиент менял объект после `lastSeenServerSequence`, а сервер получил его событие после чужого изменения того же агрегата, это кандидат в конфликт.  
  
Векторные часы полезны, чтобы отличить **каузально упорядоченные** изменения от **параллельных**: если версия A «знает» версию B, конфликт отсутствует; если ни одна не знает другую, изменения параллельны и требуют политики разрешения. [github](https://github.com/Akinmoldun/EdgeSync)  
  
### Стратегии разрешения  
  
Выбор зависит от типа данных и цены потери информации.  
  
| Подход | Как работает | Когда применять | Риск |  
|---|---|---|---|  
| Last-write-wins (LWW) | Побеждает более поздняя запись | Статусы, настройки, некритичные скалярные поля | Молчаливая потеря одной из правок; часы устройств могут расходиться.  [offlineprotocol](https://www.offlineprotocol.com/learning/offline-first/how-are-sync-conflicts-resolved) |  
| Per-field LWW | Конфликт сравнивается отдельно для каждого поля | Формы, карточки, профили: один пользователь меняет телефон, другой — адрес | Конфликт внутри одного поля всё равно теряет данные.  [github](https://github.com/jasoncrawford/claude-skills/blob/main/offline-first-sync/SKILL.md) |  
| Server-wins / client-wins | Сервер или клиент имеет приоритет | Серверные справочники, регламентированные процессы | Может отбрасывать локальную работу пользователя.  [nosqlsummer](https://www.nosqlsummer.org/blog/edge-databases-offline-first-sync-iot-2026/) |  
| Domain merge | Специальная функция объединяет обе версии по бизнес-правилам | Корзина, календарь, заказ: объединить позиции, выбрать минимальную дату и т. п. | Нужна тщательная спецификация правил.  [blog.habsi](https://blog.habsi.net/local-first-software-building-offline-first-apps-with-crdts-and-sync/) |  
| Conflict queue | Конфликт сохраняется и показывается пользователю | Финансы, медицинские данные, договоры, критичные поля | Требует UI и процесса разбора.  [hub.decision](https://hub.decision.ai/skills/microsoft/system-type-edge-offline) |  
| CRDT | Структура данных сама детерминированно сливает параллельные правки | Счётчики, множества, совместное редактирование текста, списки | Сложнее моделировать и хранить метаданные; не всегда соответствует бизнес-инвариантам.  [offlineprotocol](https://www.offlineprotocol.com/learning/offline-first/how-are-sync-conflicts-resolved) |  
| Operational Transformation (OT) | Операции преобразуются с учётом конкурирующих операций | Совместные редакторы, упорядоченный текст | Сложен в корректной реализации и обычно предполагает координирующий сервер.  [github](https://github.com/sujeet-pro/sujeet.pro/blob/main/content/articles/offline-first-architecture/README.md) |  
  
### Рекомендуемая архитектура  
  
Для большинства клиент-серверных offline-first приложений я бы использовал **гибрид**:  
  
- **Event sourcing** — как транспортный и аудиторский слой: клиент хранит локальные события, сервер принимает и упорядочивает их.  
- **Per-field LWW с логическими часами** — для обычных полей сущностей: имя, статус, комментарий, настройки.  
- **CRDT** — для данных, где параллельные правки должны сохраняться: текст, чек-листы, списки, счётчики.  
- **Conflict queue и бизнес-правила** — для критичных решений: например, одновременно изменённые цена и остаток, пересекающиеся брони, статусы платежей.  
  
Пример: два клиента офлайн меняют разные поля заказа.  
  
```text  
Клиент A: OrderStatusChanged(order-1, "confirmed")  
Клиент B: DeliveryAddressChanged(order-1, "Москва, ...")  
```  
  
Это не обязательно конфликт уровня записи: при per-field LWW обе правки могут сохраниться. Но если оба изменили `status`, нужен явный порядок: например, серверная версия побеждает, либо конфликт попадает в очередь на решение пользователя. Такой per-field подход позволяет сохранить оба независимых изменения и конфликтовать только там, где правки действительно пересекаются. [github](https://github.com/jasoncrawford/claude-skills/blob/main/offline-first-sync/SKILL.md)  
  
### Чего избегать  
  
- Не синхронизируйте «последнее состояние строки»: вы потеряете историю и не сможете корректно понять, какие изменения были параллельными.  
- Не полагайтесь только на часы устройств: используйте server sequence и/или логические часы; wall-clock time ненадёжен на офлайн-устройствах. [offlineprotocol](https://www.offlineprotocol.com/learning/offline-first/how-are-sync-conflicts-resolved)  
- Не делайте LWW универсальной стратегией: для счётчиков, текста и списков она часто уничтожает осмысленные изменения. [kbytechnologies](https://www.kbytechnologies.com/software-architecture/architecting-crdt-sync-for-offline-first-apps)  
- Не пытайтесь автоматически разрешать все конфликты: некоторые бизнес-конфликты должны быть явно показаны пользователю. [hub.decision](https://hub.decision.ai/skills/microsoft/system-type-edge-offline)  
- Не забывайте про удаления: используйте tombstone (`DeletedAt`, `isDeleted`) либо отдельное событие `EntityDeleted`, а не физическое удаление, иначе сложно корректно распространить удаление и разрешить конфликт «удалил vs изменил».  
  
### Практический минимум  
  
Для старта разумна такая схема:  
  
1. Локальная БД: таблица `events` с UUID, типом, payload, `aggregateId`, `clientId`, `lamportClock`, `createdAt`, `syncedAt`.  
2. Локальные проекции: обычные таблицы/кэш для быстрого UI.  
3. Outbox: события с `syncedAt IS NULL` отправляются пачками.  
4. Сервер: append-only журнал событий, уникальный `eventId`, серверная монотонная позиция.  
5. Pull: клиент передаёт `lastSeenServerSequence`, получает новые события и перестраивает затронутые проекции.  
6. Политики конфликтов: per-field LWW для простых полей, CRDT для совместных структур, очередь ручного разрешения для критичных бизнес-решений.  
  
Event sourcing здесь — сильный фундамент, потому что он превращает офлайн-синхронизацию из задачи «сравнить два JSON» в задачу «корректно объединить истории изменений». Но ключевой вопрос проектирования — не «использовать ли event sourcing», а **какая семантика слияния правильна для каждого типа данных вашего домена**.
